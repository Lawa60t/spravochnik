## Как проверять

```
npm run validate     # целостность базы + замок на веса
npm test             # 327 виньеток, прогон селектора, 301 случай ощущений, 101 запрос к поиску
npm run build        # стороны тела → сборка сайта → линт формулировок
```

Все должны заканчиваться без ошибок. Тестовые случаи правке под удобство не подлежат: если прогон падает, чинить нужно то, что его уронило, а не ожидание в нём. Если после правки весов тест падает — неверны веса, а не тест.

**Замок на веса.** `tools/check-weights.js` снимает отпечаток с `condition`, `base`, `weights` и `stop` по каждому из 124 разделов и падает при любом изменении. Проверено опытом: подделанный вес 327 виньеток не замечают.

## Как устроена база

Две отдельные полки:

- **Статьи о состояниях** (`conditions-*.json`) пишутся один раз. Пневмония нужна в девяти разделах, но существует в одном экземпляре.
- **Разделы справочника** (`syndromes-*.json`) текста о болезнях не содержат — только ссылки на статьи и веса признаков.

Поэтому наполнять «по областям» нельзя: получатся дубли, которые со временем разъедутся.

## Поля статьи

| Поле | Назначение |
|---|---|
| `what` / `who` / `urgent` / `doctor` / `tests` | Короткие справочные строки для списков разделов |
| `detail` | Подробная статья: массив блоков `{h, p}`, 5–7 блоков, 330–500 слов. Проверяется отдельным списком `DETAIL_FORBIDDEN` в `tools/validate.js` |
| `emergency` | Красная плашка «Это состояние может угрожать жизни». Порог — «счёт идёт на часы», и он не смягчается |
| `redflag` | Место статьи в блоке «редко, но важно не пропустить». Плашки НЕ даёт: справочник, который пугает каждого третьего, перестают читать |
| `alt` | Обиходные имена для находимости. Синоним, дословно повторяющий название, валидатор запрещает |
| `sexOnly` (30 статей), `ageMin`/`ageMax` (14 статей) | Внематочная беременность не покажется мужчине, височный артериит не всплывёт у тридцатилетнего |
| `status` | У всех 364 — `compiled`: сверено с источником, врачом не проверялось |

## Веса

Ключ веса — `идВопроса_идОтвета`, например `plaque_grey`.

| Значение | Смысл |
|---|---|
| +4…+6 | Патогномонично: почти не бывает при других состояниях |
| +2…+3 | Сильно за |
| +1 | За |
| −2…−3 | Против |
| −4…−6 | Почти исключает |

Ответ «не знаю» веса не имеет нигде — валидатор это проверяет и не пропустит.

**Стоп-факторы важнее больших отрицательных весов.** У кандидата может быть поле `stop` — список ответов, полностью исключающих состояние. Отрицательный вес перевешивается суммой положительных: удалённый аппендикс с весом −6 всё равно проигрывал восьми совпавшим признакам аппендицита. Отсутствующий орган воспалиться не может, поэтому это `stop`, а не вес. Сейчас таких правил восемь.

## Ощущения и подразумеваемые ответы

**`feelings`** — массив объектов `{ text, implies?, favors? }`. Выбор ощущения на странице раздела подставляет ответы и перестраивает список. `implies` — ответы, которые ощущение означает буквально; `favors` — прямая надбавка 3–5, крайняя мера для случаев, когда подходящего вопроса в разделе нет. Размечены все 124 раздела, обоснование каждого решения — в `tools/feelings-markup.json`.

**`implies` у раздела** — ответы, верные по определению. В разделе «потеря веса» человека не спрашивают, теряет ли он вес: движок подставляет ответ до расчёта и до проверки красных флагов.

**`focused: true`** (10 разделов) — жанр раздела-витрины: названные состояния, находятся поиском. Освобождает от «≥5 состояний» и «≥2 тревог», но `notSearchedHere` обязателен.

## Слой красных флагов

`redflags.json` работает **поверх** разделов и не зависит от полноты списков. Если в дифференциальный ряд что-то не попало по недосмотру, сочетание признаков всё равно сработает.

Набор намеренно короткий (68 правил) и состоит из общеизвестных неотложных сочетаний — именно поэтому его можно составить надёжно, в отличие от длинных списков.

**Привязка к зонам.** У правила может быть поле `zones` — тогда оно работает только там. Это появилось после того, как правило про мгновенно возникшую боль со рвотой, написанное для головы, сработало на малярии.

**Возрастные границы.** `minAge`/`maxAge` нужны там, где состояние строго возрастное. Височный артериит практически не бывает до пятидесяти.

**Исключения.** Поле `unless` подавляет правило при определённых ответах. Слабость в обеих ногах — признак сдавления спинного мозга, но при стенозе позвоночного канала она проходит от наклона вперёд: это позиционная хромота, а не катастрофа.

## Слой якорей

`anatomy.json` связывает точку на модели тела с разделом. Координаты заданы **не в пикселях**, а в долях от габарита фигуры: `u` по горизонтали (0.5 — осевая линия), `v` по вертикали (0 — макушка, 1 — подошвы).

Чтобы прикрепить базу к новой модели, нужно заполнить четыре числа калибровки:

```
X = axisX + (u - 0.5) * 2 * halfWidth
Y = crownY + v * (soleY - crownY)
```

Все участки пересчитываются формулой, ничего не перерисовывается руками. У каждого участка есть ещё `landmark` — ориентир словами: если пропорции новой модели отличаются, участок восстанавливается по нему.

**Стороны:** `right` и `left` — стороны тела, не экрана. На виде спереди правая сторона тела находится слева на экране. Проверяется на сборке `tools/check-anatomy.js`, несовпадение роняет сборку.

Жалобы, которые нельзя показать пальцем — тошнота, головокружение, кровь в стуле — собраны в отдельный вход `symptom.list` без якоря.

## Поиск

Поиск в шапке и фильтр указателя сравнивают слова **по основам**, а не подстроки: стеммер Портера для русского языка написан в `src/site/assets/poisk.js`, зависимостей у проекта нет. «болит», «боли» и «боль» дают одну основу; «высокая» и «невысокая» — разные.

Поиск ведёт к постоянному адресу раздела или статьи. Это оглавление, а не разбор случая: подсказок «похоже, у вас…», процентов совпадения и разбора набранного текста как жалобы здесь нет и не будет. Запрос не попадает в адрес и нигде не сохраняется.

Проверяется прогоном `tools/test-poisk.js` по `tools/poisk-cases.json`: 101 запрос, написанный так, как его набирает человек, 105 проверок. Прогон гоняет ровно тот файл, который уезжает в браузер.
